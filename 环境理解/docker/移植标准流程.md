
第一种是 **源码重建型迁移**：把代码、Dockerfile、docker-compose.yml、.env、数据库备份带到云服务器，在云服务器上重新 build image，再创建 container。

第二种是 **镜像搬运型迁移**：把当前已经构建好的 image 直接导出，传到云服务器，然后在云服务器上用这些 image 创建 container。

这两种方法都要注意一个核心点：**PostgreSQL 数据不在 image 里，必须单独迁移数据库数据**。否则你只迁移了运行环境，数据库内容会是空的或重新初始化的。🌱

## 方法一：在云服务器上用同一套 docker-compose.yml 重新创建容器

这种方式最推荐用于长期开发、正式部署、可维护项目。它的本质是：

```text
源码 + Dockerfile + docker-compose.yml + .env + 数据库备份
→ 云服务器重新 docker compose build
→ 生成新的 image
→ 创建新的 container
→ 恢复数据库
```

这些是迁移的核心。`backend/` 和 `frontend/` 里通常包含 Dockerfile，也就是构建镜像的规则。

### 第 2 步：导出 PostgreSQL 数据库

推荐使用 `pg_dump`，不要直接复制数据库 volume。因为 `pg_dump` 是数据库层面的备份，跨服务器、跨平台更稳定。

在原平台执行：

```bash
docker exec -t flowtrace-db pg_dump \
  -U flowtrace \
  -d flowtrace \
  -Fc \
  -f /tmp/flowtrace.dump
```

解释：

```text
docker exec -t flowtrace-db
```

表示进入正在运行的数据库容器执行命令。

```text
pg_dump
```

表示导出 PostgreSQL 数据库。

```text
-U flowtrace
```

表示数据库用户名是 `flowtrace`。

```text
-d flowtrace
```

表示要导出的数据库名是 `flowtrace`。

```text
-Fc
```

表示导出为 PostgreSQL 自定义格式，后续适合用 `pg_restore` 恢复。

```text
-f /tmp/flowtrace.dump
```

表示把备份文件保存到容器内部的 `/tmp/flowtrace.dump`。

然后把备份文件从容器复制到宿主机：

```bash
docker cp flowtrace-db:/tmp/flowtrace.dump ./flowtrace.dump
```

解释：把数据库容器里的备份文件复制到当前项目目录下。

检查是否成功：

```bash
ls -lh flowtrace.dump
```

### 方法一总结

这种方法的核心命令是：

```bash
git clone 项目仓库
docker compose --env-file config/.env -f docker-compose.yml up -d --build
docker cp flowtrace.dump flowtrace-db:/tmp/flowtrace.dump
docker exec -it flowtrace-db pg_restore -U flowtrace -d flowtrace --clean --if-exists /tmp/flowtrace.dump
```

它的优点是：

```text
最规范
最适合长期维护
代码、Dockerfile、compose 都是可追踪的
新平台可以重新构建完整环境
```

缺点是：

```text
云服务器需要能联网拉取基础镜像和依赖
build 时间可能较长
依赖没锁死时，重新 build 可能和旧环境略有差异
```

## 方法二：直接移植 image 到云服务器运行

这种方式适合你想把当前已经构建好的运行环境直接搬过去。它的本质是：

```text
当前平台已有 image
→ docker save 导出 image
→ scp 上传云服务器
→ docker load 导入 image
→ 用 docker-compose.yml 基于 image 创建 container
→ 恢复数据库
```

注意：这个方法依然需要 `docker-compose.yml` 和 `.env`。因为 image 只是镜像，Compose 才负责把数据库、后端、前端组织起来运行。

---

### 第 0 步：确认当前 image 名称

在原平台执行：

```bash
docker images
```

根据你的截图，主要 image 可能是：

```text
v1-backend:latest
v1-frontend:latest
postgres:16
```

解释：

```text
v1-backend:latest
```

是你的后端业务镜像。

```text
v1-frontend:latest
```

是你的前端业务镜像。

```text
postgres:16
```

是 PostgreSQL 官方数据库镜像。

如果云服务器可以联网，`postgres:16` 不一定要导出，因为云服务器可以自己 pull。

如果云服务器不能联网，就一起导出。

---

### 第 1 步：导出业务 image

在原平台执行：

```bash
docker save -o v1-backend.tar v1-backend:latest
docker save -o v1-frontend.tar v1-frontend:latest
```

解释：

```text
docker save
```

用于把 Docker image 导出成 `.tar` 文件。

```text
-o v1-backend.tar
```

指定输出文件名。

```text
v1-backend:latest
```

指定要导出的镜像名和 tag。

如果你还要导出 PostgreSQL：

```bash
docker save -o postgres-16.tar postgres:16
```

检查文件大小：

```bash
ls -lh *.tar
```

---

### 第 2 步：导出 PostgreSQL 数据库

即使你迁移 image，也必须单独导出数据库。执行：

```bash
docker exec -t flowtrace-db pg_dump \
  -U flowtrace \
  -d flowtrace \
  -Fc \
  -f /tmp/flowtrace.dump
```

然后复制出来：

```bash
docker cp flowtrace-db:/tmp/flowtrace.dump ./flowtrace.dump
```

解释：这一步和方法一一样，因为数据库数据不在 `postgres:16` 这个 image 里。

---

### 第 3 步：准备 compose 配置文件

你仍然需要迁移 compose 文件和环境变量文件：

```bash
tar -czf flowtrace-compose-config.tar.gz \
  docker-compose.yml \
  docker-compose.dev.yml \
  config
```

如果没有 `docker-compose.dev.yml`，就不要写它：

```bash
tar -czf flowtrace-compose-config.tar.gz \
  docker-compose.yml \
  config
```

解释：把 compose 文件和 `.env` 打包。云服务器需要它们来创建容器、配置端口、配置环境变量、挂载 volume。

---

### 第 4 步：把 image、compose 配置、数据库备份上传到云服务器

执行：

```bash
scp v1-backend.tar v1-frontend.tar flowtrace.dump flowtrace-compose-config.tar.gz \
  root@你的服务器IP:/root/
```

如果包含 PostgreSQL 镜像：

```bash
scp postgres-16.tar root@你的服务器IP:/root/
```

解释：把镜像 tar 包、数据库备份、compose 配置传到云服务器。

---

### 第 5 步：登录云服务器

执行：

```bash

```

解释：


### 第 9 步：确保 docker-compose.yml 使用的是 image，而不是 build

这是方法二最关键的点。

你的 compose 文件里如果是这样：

```yaml
backend:
  build:
    context: ./backend
  image: v1-backend
```

或者：

```yaml
frontend:
  build:
    context: ./frontend
  image: v1-frontend
```

那在执行 `docker compose up` 时，如果加了 `--build`，它还是可能尝试重新构建。

如果你想强制使用已经导入的 image，建议云服务器上的 compose 改成：

```yaml
backend:
  image: v1-backend:latest
  container_name: flowtrace-backend
  restart: unless-stopped
  env_file:
    - config/.env
  ports:
    - "8000:8000"
  depends_on:
    - db

frontend:
  image: v1-frontend:latest
  container_name: flowtrace-frontend
  restart: unless-stopped
  ports:
    - "5173:80"
  depends_on:
    - backend
```

数据库类似：

```yaml
db:
  image: postgres:16
  container_name: flowtrace-db
  restart: unless-stopped
  environment:
    POSTGRES_DB: ${POSTGRES_DB:-flowtrace}
    POSTGRES_USER: ${POSTGRES_USER:-flowtrace}
    POSTGRES_PASSWORD: ${PG_PASSWORD:-flowtrace_dev}
  volumes:
    - pg_data:/var/lib/postgresql/data
  ports:
    - "${PG_PORT:-5433}:5432"
```

如果你不想改原来的 `docker-compose.yml`，可以新建一个专门用于云端 image 部署的文件：

```bash
nano docker-compose.prod.yml
```

然后写入 image 版本配置。

```bash
docker load -i v1-frontend.tar

docker compose --env-file config/.env -f docker-compose.yml up -d

docker cp flowtrace.dump flowtrace-db:/tmp/flowtrace.dump
docker exec -it flowtrace-db pg_restore -U flowtrace -d flowtrace --clean --if-exists /tmp/flowtrace.dump
```

它的优点是：

```text
不用在云服务器重新 build
更容易复刻当前可运行环境
适合云服务器不能联网或网络很慢的情况
适合当前 image 是稳定版本、想快速部署
```

缺点是：

```text
image 文件通常很大，上传慢
不如源码部署可维护
如果 compose 里仍然写 build，容易误触发重新构建
不同 CPU 架构可能无法运行
```

最后这个点尤其重要：如果你当前是在 Mac M1/M2 上构建的 arm64 镜像，而云服务器是 x86_64 架构，那么直接导出的 image 可能跑不起来。你可以检查架构：

```bash
docker image inspect v1-backend:latest --format '{{.Architecture}}'
```

如果输出：

```text
arm64
```

而云服务器是：

```bash
uname -m
```

输出：

```text
x86_64
```

那就不适合直接移植 image。此时更推荐方法一：在云服务器上重新 build。

---

## 两种方式怎么选？

你的量化平台项目，我建议这样选：

```text
日常开发迁移 / 换电脑 / 上云部署：
优先用方法一，也就是源码 + compose + pg_dump。

临时复制当前可运行环境 / 云服务器不能联网 / 不想重新 build：
使用方法二，也就是 docker save + docker load + compose up。

数据库：
无论方法一还是方法二，都用 pg_dump / pg_restore 单独迁移。
```

最稳的云端标准方案是：

```text
Git 管理代码
Dockerfile 管理环境
docker-compose.yml 管理服务编排
.env 管理环境变量
pg_dump 管理数据库迁移
云服务器重新 docker compose up -d --build
```

你可以把它理解成：**image 是可以重新生成的“结果”；代码、Dockerfile、compose、数据库备份才是迁移的“根本资产”。** 🚀
